# État d’Azur — 2 octobre 2026

Azur est un ensemble d’outils Windows en C# pour administrer un serveur Dofus Retro, consulter ses ressources, créer des objets, modifier des cartes et utiliser un client bot. Le logiciel principal est une application WinForms .NET Framework 4.8. `Tools_protocol` fournit la configuration, les accès SQL et les ressources ; `Tool_Editor` fournit les fonctions d’édition ; `Tool_BotProtocol` contient le client et le protocole du bot.

Le README décrit aussi des fonctions qui restent à développer. Les compilations **Debug et Release réussissent**, et les **29 tests passent dans chacune de ces configurations** le 2 octobre 2026 : 21 sans base et 8 d'intégration, dont le contrôle du schéma réel de `kauth`. Ces contrôles ne remplacent pas la validation avec un client et un serveur de jeu.

## Vérification reproductible

```powershell
.\tests\Run-Tests.ps1
.\tests\Run-Tests.ps1 -Integration
.\tests\Run-Tests.ps1 -Configuration Release -Integration
```

La suite contient **36 tests** : vingt-sept sans base, neuf avec une instance MySQL 8.4 indépendante. Le serveur de test utilise le port `43306`, possède un dossier de données neuf et est arrêté à la fin. La configuration SQL du logiciel n’est jamais utilisée par cette suite. Voir [les instructions des tests](../tests/README.md).

Les tests réseau et de conversion couvrent le décodeur et le relais TCP local (fragments, UTF-8, masquage, fermeture partielle, arrêt et redémarrage), le transport du bot et le cycle de connexion des comptes, puis le convertisseur de cartes et l'interface de capture. Ils vérifient les 479 cellules, la conservation des métadonnées AME, les filtres, la vue compacte et l'arrêt du relais à la fermeture du gestionnaire. Tous les échanges réseau utilisent des messages fictifs sur la boucle locale.

`KauthSchemaIntegrationSmoke` reproduit les 58 tables de `kauth-schema.sql`, vérifie les correspondances et les ressources, puis utilise des comptes et personnages fictifs pour les parcours de création, consultation et sauvegarde. Il couvre notamment les contraintes SQL strictes, les états de connexion inconnus, les limites de colonnes, les couleurs et le point de sauvegarde, ainsi que les refus liés aux conflits et au compte cible. Voir [la compatibilité kauth](KAUTH_COMPATIBILITE.md).

`StarLocoSchemaIntegrationSmoke` recrée les 27 tables `login` et 47 tables `game` du dump StarLoco, vérifie que les 58 tables du profil existent dans la base attendue et que les 24 éditeurs lisent `game`, puis déroule avec des données fictives les comptes, personnages, métiers/sorts entre les deux bases, l'inventaire dans `world.entity.objects`, la création d'objets, les éditeurs de sorts/cartes/modèles/panoplies/butins/métiers, la recherche, les placements, l'export XML du bot et la modération. Voir [la compatibilité StarLoco](STARLOCO_COMPATIBILITE.md).

Les tests couvrent notamment les transactions annulées, les personnages connectés, les tables MyISAM refusées, les schémas d’objets à 15 et 16 colonnes, la conservation des fichiers lors d’un export invalide, la lecture du XML par le bot, les cartes chiffrées et les outils graphiques. Les tests supplémentaires vérifient les 24 schémas fournis, la présentation et les champs des éditeurs, la synchronisation numérique, les couleurs, les formats structurés, le CRUD des nouvelles ressources et les liens entre modèles/panoplies. Le test SWF vérifie les constantes AVM1, les imports compressés, les cellules actives et les huit déplacements, ainsi que les cartes de 19 801 cellules. Les objets SWF disposent aussi d'un lecteur indépendant, d'une fixture assemblée séparément et de tests de conservation des balises, propriétés supplémentaires, plusieurs fiches et brouillons graphiques. Voir [les cartes SWF](FORMAT_SWF_CARTES.md) et [les objets SWF](FORMAT_SWF_OBJETS.md).

Le placement des tuiles utilise maintenant les limites des pixels visibles, sans compter les marges transparentes, pour ancrer les sols au centre et les objets au pied quand les fichiers n'indiquent aucune position. Les tests vérifient les pixels dessinés, une vraie tuile livrée avec Azur et la cellule repérée par la souris, même après ajustement du document. La lecture de l'inventaire se réessaie après une panne de la connexion world et remonte une cause explicite au lieu de laisser toutes les fiches sous « détails non chargés ».

Les six contrôles spécifiques ajoutés au bot couvrent configuration/DPAPI, parcours Login → Game fictif, cartes/actions/métiers, sorts, rendu de carte et interface. `BotMapViewSmoke` vérifie les couches PNG, les fichiers libérés, les marges transparentes, les ressources absentes, puis la précision des cellules après zoom, déplacement et redimensionnement. `BotUiSmoke` produit des captures natives (PrintWindow, pour préserver l’ordre des panneaux), utilise les vrais décors Nowel/Astrub et vérifie notamment la grande carte, les fiches refermables et la discussion privée à la taille minimale.

Le fichier `F:\Téléchargements\kauth.sql` fourni contient désormais les tables `accounts`, `players` et les ressources statiques. Seules ses 58 définitions de tables sont reprises dans les fixtures ; aucune ligne réelle n'est importée par les tests ni incluse dans la distribution. La connexion auth doit viser kauth et la connexion world les exemplaires `items` de kworld. Les correspondances personnalisées existantes restent conservées et peuvent nécessiter un ajustement dans la configuration.

Le kit `F:\kit` fourni contient désormais les serveurs **StarLoco Login et Game** et un client **Dofus 1.34**. La validation en jeu reste à effectuer : connexion du bot, déplacements, combat, chargement des SWF exportés et comportement des placements. Les validations SQL de kauth ciblent **Kryone** ; les essais réseau avec **StarLoco** constituent un parcours distinct. Les noms et structures de leurs bases ne doivent pas être traités comme des correspondances interchangeables.

Le cycle import/modification/export/réouverture des cartes est vérifié dans Azur et par un lecteur SWF indépendant. Les éditeurs et leur persistance disposent de formulaires thémés et de tests. Voir [leur guide](GUIDE_EDITEURS.md). Les critères ci-dessus restent nécessaires avant de déclarer le projet terminé.
