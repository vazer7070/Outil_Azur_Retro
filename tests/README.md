# Vérification d’Azur

Dernière exécution complète : **29 tests réussis en Debug et Release le 2 octobre 2026**. Le test kauth couvre aussi les conflits entre deux fenêtres, la conservation des valeurs d'origine et le refus des caractères incompatibles avec les colonnes `latin1` sans changement de la base ni du cache.

Depuis la racine du dépôt, dans PowerShell :

```powershell
.\tests\Run-Tests.ps1
.\tests\Run-Tests.ps1 -Integration
.\tests\Run-Tests.ps1 -Configuration Release -Integration
```

Visual Studio avec MSBuild et le ciblage .NET Framework 4.8 doit être installé. Les tests d’intégration nécessitent MySQL 8.4 ; son dossier peut être indiqué avec `-MySqlBin 'C:\chemin\mysql\bin'`. `-NoBuild` utilise les binaires déjà compilés pour la configuration choisie. Chaque test dispose d’un délai de 90 secondes par défaut, ajustable avec `-TestTimeoutSeconds` ; ses journaux stdout/stderr sont conservés dans le dossier de l’exécution.

Avant la première compilation sur une nouvelle machine, restaurez les packages NuGet de la solution dans Visual Studio. Les bibliothèques d’interface Syncfusion et leur version sont maintenant déclarées dans le projet et dans `packages.config`.

Les vingt-neuf tests sans base vérifient les modifications en attente, la génération SQL et les jets d'objets, la recherche, les cartes et leurs codecs/projets/ressources, les imports/exports SWF et l'annulation de fermeture. Ils vérifient aussi les formulaires des anciens éditeurs, le menu atelier et les 24 éditeurs de ressources à partir des définitions de tables fournies. Aucune ligne utilisateur du dump n'est importée pour les fixtures.

Les tests réseau et de conversion utilisent uniquement la boucle locale et des messages fictifs : `NetworkCaptureSmoke` couvre le décodeur UTF-8/NUL, la transmission du relais dans les deux sens, le masquage, les connexions distinctes, la fermeture partielle, l'arrêt et le redémarrage ; `BotTransportSmoke` vérifie les sessions, grands envois complets, erreurs, sémaphore, reconnexions et état des comptes ; `ResourceManagerSmoke` contrôle les 479 cellules, la conservation AME et des données importées, les filtres et la vue compacte de capture, ainsi que l'arrêt du relais à la fermeture du gestionnaire. Aucun serveur utilisateur n'est contacté. Voir [le guide de capture](../docs/CAPTURE_RESEAU.md).

Le test SWF utilise aussi SwfDotNet comme lecteur indépendant. Pour cette seule vérification, restaurez `tests/packages.config` dans le dossier `packages` du dépôt (`nuget restore tests/packages.config -PackagesDirectory packages`). Il utilise log4net 2.0.17, compatible avec l’ancien lecteur ; l’application conserve sa propre version. Les tests couvrent FWS/CWS, les constantes AVM1, les cellules actives, les huit types de déplacement, les grandes cartes, les fichiers corrompus et la conservation d’un export existant en cas d’erreur. `Fixtures/10000_0612041200.swf` provient du pack « Ile Nowel » fourni par l'utilisateur (auteur indiqué : Kenzhu) et vérifie les 479 cellules, la version du fichier, les autorisations 98 et l'export identique des données de carte. `Fixtures/azur-v2.ame` vérifie l'ajout de la dernière cellule lors de la lecture d'un ancien projet. Voir [le format pris en charge](../docs/FORMAT_SWF_CARTES.md).

Les neuf tests d'intégration vérifient inventaire/modération/création d'objets, XML du bot, triggers/donjons, sorts/métiers des personnages, CRUD des ressources et compatibilité des schémas kauth et StarLoco. Ils couvrent les transactions annulées, personnages connectés, moteurs MyISAM refusés, schémas d'objets à 15/16 colonnes, effets critiques, liens réciproques modèles/panoplies, références d'ingrédients et butins, AUTO_INCREMENT, lignes sans clef unique ou ambiguës, NULL, SQL complet et édition des exemplaires/conflits/emplacements.

`KauthSchemaIntegrationSmoke` utilise `Fixtures/kauth-schema.sql`, extrait des **58 CREATE TABLE InnoDB** du fichier `F:\Téléchargements\kauth.sql` fourni. La fixture ne contient aucune insertion ni compte réel. Le test vérifie les 50 correspondances auth par défaut, les 24 familles de ressources et les variantes de placements, puis crée ses comptes et personnages fictifs. Les parcours couvrent la création en SQL strict et sa relecture, les schémas compatibles plus petits, les champs obligatoires inconnus et moteurs refusés, les états de connexion NULL, les limites réelles des colonnes, les couleurs/points de sauvegarde, les conflits et le compte cible. La validation finale doit réussir en Debug et Release avant la diffusion ; voir [la compatibilité kauth](../docs/KAUTH_COMPATIBILITE.md).

`StarLocoSchemaIntegrationSmoke` utilise `Fixtures/starloco-login-schema.sql` (**27 CREATE TABLE**) et `Fixtures/starloco-game-schema.sql` (**47 CREATE TABLE**), extraits du dump StarLoco fourni par l'auteur le 3 octobre 2026, convertis en InnoDB, sans valeur AUTO_INCREMENT ni ligne de données. Il écrit et relit la configuration StarLoco (auth = `login`, world = `game`), vérifie que les 58 tables du profil existent dans la base attendue, que les noms du profil priment sur les JSON de correspondance et que les 24 éditeurs lisent `game`. Avec des données fictives, il déroule ensuite la création et l'édition des comptes (SHA512/MD5, doublon, MyISAM), les personnages (couleurs, point de sauvegarde, renommage, `logged` NULL, refus, 30 caractères), les métiers et sorts lus dans `game` pour un personnage de `login`, l'inventaire dans `world.entity.objects` (colonnes `id`/`quantity`/`position`), la création d'un modèle, d'une recette, d'une panoplie et d'un exemplaire répartis entre les deux bases, les éditeurs de sorts (`duration`), cartes (sans `cells`/`background`), modèles, panoplies, butins (sans `id`) et métiers avec leurs exports SQL, les caches et la fenêtre de recherche, les placements d'une carte, l'export XML du bot et la suppression de personnages et de comptes ; voir [la compatibilité StarLoco](../docs/STARLOCO_COMPATIBILITE.md).

Le test d'inventaire simule aussi une connexion world absente, vérifie le diagnostic affichable puis restaure la connexion et vérifie que les objets et quantités sont relus. Le test de cartes compare les pixels de sols et d'objets à l'ancrage de la cellule, puis contrôle le ciblage de la souris après le redimensionnement de la fenêtre. Il vérifie le dessin et le masquage des repères serveur, le filtrage des cellules hors carte et les deux variantes d'enclos avec/sans `cellid`. L'intégration charge les quatre familles de placements depuis MySQL isolé et contrôle qu'une autre carte ne se mélange pas à la carte ouverte.

Le script démarre une instance MySQL dédiée sur `127.0.0.1:43306`, dans un nouveau dossier sous `tests/bin`, puis l’arrête en fin d’exécution. Il refuse de continuer si ce port est déjà utilisé. Il ne lit pas la configuration des bases du logiciel et n’utilise aucun service MySQL existant. Les tests créent et suppriment seulement leurs propres schémas temporaires. Les journaux et données du serveur de test restent dans le dossier ignoré `tests/bin` pour le diagnostic.

Le paquet Release portable se construit avec `tools/Build-PortableRelease.ps1`. `python tests/verify_portable.py chemin/du/paquet.zip` relit les empreintes SHA-256 de chaque fichier, vérifie les ressources nécessaires et refuse toute configuration locale ou chemin de sortie dangereux dans l'archive.

Le test `ItemClientSwfSmoke` vérifie la compilation des objets et leur intégration dans une copie, avec un lecteur indépendant et une fixture assemblée séparément. Il couvre l'ordre des paramètres d'arme, UTF-8, constantes/constructeurs/registres, nombres, compression, propriétés supplémentaires, plusieurs fiches, identifiants espacés, doublons, corruption et conservation des balises/fichiers. Les tests d'interface modifient aussi des champs client, changent de fiche et relisent les valeurs dans le SWF exporté. Voir [les objets SWF](../docs/FORMAT_SWF_OBJETS.md).

Ces tests ne valident pas le protocole avec un vrai serveur StarLoco, l’ouverture des SWF dans le client Dofus ni les anciens fichiers AME d’Astria.

Les tests peuvent aussi être compilés un à un avec `csc` contre `Outil_Azur_complet/bin/Debug` et lancés sous Mono/Linux (`MONO_PATH` et `AZUR_TEST_BIN` pointant sur ce dossier, exécutables placés dans `tests/bin`). Le 3 octobre 2026, 21 tests sans base (dont `BotClientSkinSmoke`, `BotDialogsSmoke` et `BotShopSmoke`) et 6 tests d'intégration (inventaire, modération, création d'objets, édition serveur, schémas kauth et StarLoco) passent ainsi sur une instance MySQL 8.0 isolée. Les autres dépendent de Windows (`uxtheme`, `GetDC`, `PrintWindow`, chemins `.\ressources`), de fonctions non implémentées par Mono ou des ressources graphiques non versionnées : la validation complète reste `Run-Tests.ps1` sous Windows.
